# vLLM TPS probe — desktop, 2026-08-18

A quick, **non-scientific** throughput probe of the desktop inference server
(`http://192.168.0.80:8000/v1`), run to answer "how fast is inference, and
does the 350 W GPU power cap matter?" It directly motivated the 350 → 450 W
power-cap change (commit `719b669`, `machines/desktop/default.nix`). The
probe is backend-agnostic (plain OpenAI chat-completions client), so the
same `probe.py` was re-run the same day against **SGLang + DSpark**
(speculative decoding, TP=2) after the `switch-qwen38-backend-v2.sh sglang`
switch.

## Environment

- **Host**: desktop (192.168.0.80) — 2× RTX PRO 6000 Blackwell Workstation
  (96 GB), Ryzen 9 9950X, NixOS, driver 575.57.08-era stack, vLLM OpenAI API
  at `http://192.168.0.80:8000/v1`
- **Model**: `qwen3.8-27b` (BF16), TP=2, `gpu_memory_utilization≈0.975`,
  context 262144
- **Probe**: `probe.py` in this directory — one streamed chat completion,
  `temperature=0`, ~60-token prose prompt ("explain how a hash map works"),
  decode TPS = `(completion_tokens − 1) / (total − TTFT)`, usage from
  vLLM's final stream chunk

## Method caveats (why "non-scientific")

- Single stream, single short prompt, one run per cell (the SGLang cells
  were repeated once). No warm-cache control, no concurrency, no
  long-context prefill test.
- **Self-interference**: the measuring session itself ran on the same GPUs
  (this is the box that serves pi), so every cell shares that background
  load. The 350-vs-450 W comparison is still valid *relative*, since both
  sides had it.
- Thinking tokens stream in the `reasoning` delta field (NOT
  `reasoning_content`); answer tokens in `content`. TTFT below is time to
  the first **answer** token, so with thinking on it includes the whole
  reasoning phase.

## SGLang + DSpark, same day @ 450 W

After switching :8000 to the `qwen38-27b-bf16-dspark-sglang-v2` profile
(SGLang, DSpark speculative decoding, TP=2, gamma=7), the identical probe
cells:

| Run | Thinking | completion | TTFT | total | DECODE TPS |
|---|---|---|---|---|---|
| warmup | off | 64 | 0.09 s | 0.83 s | 85.2 |
| A | off | 512 | 0.09 s | 6.15 s | **84.2** |
| A (repeat) | off | 512 | 0.09 s | 6.16 s | **84.2** |
| B | xhigh | 1500 | 2.22 s | 16.87 s | 102.4 (blended) |
| B (repeat) | xhigh | 1500 | 3.04 s | 16.78 s | 109.1 (blended) |

### vLLM vs SGLang+DSpark @ 450 W

| Cell | vLLM | SGLang+DSpark | Δ |
|---|---|---|---|
| thinking-off, 512 tok (decode) | 83.3 tok/s | 84.2 tok/s (×2 runs) | ≈ parity |
| xhigh, 1500 tok (total wall) | 23.46–25.37 s | **16.78–16.87 s** | **~1.4–1.5× faster** |
| xhigh thinking phase (first reasoning → first answer) | 3.8–4.7 s | 2.1–2.9 s | ~1.7× faster |
| prefill TTFT (thinking off) | 0.06 s | 0.09 s | ≈ parity |

### Why the split (from SGLang's own `/metrics`, cumulative since boot)

- `spec_num_draft_tokens=8`, `spec_accept_rate=0.35`,
  `spec_accept_length=3.45` — the DSpark draft proposes 8 tokens and ~3.5
  get accepted per verify step.
- **Plain prose is near breakeven** at that acceptance rate (84.2 vs 83.3
tok/s): the 8-token verify + 7 draft steps cost about what the ~3.5 accepted
tokens save. That is why the thinking-off cell matches vLLM.
- **The win concentrates in the thinking phase** (2.1–2.9 s vs 3.8–4.7 s):
  thinking traces are short, predictable, and the draft clearly accepts them
  far above the blended 35 % — which also explains why the *blended* xhigh
total (16.8 s) beats vLLM (23.5–25.4 s) by 1.4–1.5×.
- Raw inter-token latency across all 10 requests: 10817 samples / 118.5 s
  ≈ 11 ms mean (≈91 tok/s), consistent with the per-cell numbers under
  mixed traffic.
- `spec_verify_calls_total=4481`, decode CUDA-graph passes 4492 — compact
  ragged-verify graphs are doing the work.
- Thermals at 450 W: 71 / 61 °C, ~368 W draw even idle (persistence
  daemon); comfortable.

## Findings

1. **The 350 W cap was hard-throttling.** Under load both cards sat pinned
   at 349.9 W / 100 % util. Raising the cap to 450 W bought
   **~+20–25 % decode throughput** (67 → 83 tok/s clean answer; 77 → ~105
   tok/s blended with xhigh thinking) for free.
2. **Prefill is effectively instant** for short prompts: ~0.06–0.25 s
   TTFT with thinking off.
3. **Thinking costs latency, not throughput.** xhigh spends 2.5–4.8 s
   reasoning before the first answer token; the answer then streams at the
   normal rate. Total time ≈ thinking time + tokens/~85.
4. **Thermals at 450 W are comfortable**: GPU0 73 °C / 421 W, GPU1
   61 °C / 395 W sustained — ~20 °C of headroom before throttle.
5. **The CPU is the hot spot, not the GPUs**: Ryzen package at 93.9 °C
   (Tcase throttle point ~95 °C) while doing modest work — it bakes in a
   chassis full of ~800 W of GPU heat. New CPU cooler ordered
   (2026-08-18); a hot CPU/VRM can erode PCIe signal margin, which matters
   for the Xid 79 history in `docs/runbooks/gpu-inference-crash-triage.md`.
6. **SGLang+DSpark vs vLLM @ 450 W (same day)**: parity on plain-prose
   decode (~84 tok/s both); **1.4–1.5× end-to-end on thinking workloads**
   (xhigh 1500-tok: 16.8 s vs 23.5–25.4 s), driven by the thinking phase
   where DSpark's draft acceptance is high (blended `spec_accept_length`
   3.45/8, `spec_accept_rate` 0.35). At current acceptance, DSpark is
   roughly breakeven for pure prose — worth re-profiling the SPS table if
   prose TPS becomes the target.

## Re-running

```sh
python3 benchmarks/vllm-tps/probe.py --thinking off
python3 benchmarks/vllm-tps/probe.py --thinking xhigh --max-tokens 1500
```

Works against whichever backend owns :8000 (vLLM or SGLang) — both serve the
same OpenAI-compatible API and model name. On SGLang, grab
`/metrics` after a run for `spec_accept_length` / `spec_accept_rate`.

If you want a *scientific* pass: vLLM's `benchmark_serving.py` (or
`vllm bench serve`) against the same endpoint — concurrency sweep,
input/output length matrix, and a long-context prefill cell.
