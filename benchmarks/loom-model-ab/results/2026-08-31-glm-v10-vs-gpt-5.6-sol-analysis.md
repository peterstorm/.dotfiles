# GLM v10 versus GPT-5.6 Sol — UI-relay v2 analysis

Date: 2026-08-31

## Scope and caveat

This compares one mechanically valid, unblinded UI-relay protocol-v2 planning run from each model:

- local GLM v10: `20260831T122019Z-glm-v10-dcp2-1`;
- GPT-5.6 Sol: `20260831T143720Z-sol-1`.

Both runs used the same protocol hash, reached the exact planning-only boundary, kept every task pending, preserved frozen files, and attested all planning children to the intended model. The Sol run used the later Loom `3de455c` baseline after fixing harness defects exposed by GLM; those defects were excluded from GLM's semantic grade.

One repetition per model is descriptive evidence, not a statistically meaningful winner declaration. The benchmark also does not establish either model's parameter count. Even accepting the premise that Sol is a much larger cloud model, this comparison measures planning artifacts—not parameter efficiency, serving cost, latency, privacy, or operational control.

## Requirement discovery favors GLM slightly

| Discovery | GLM v10 | Sol |
|---|---:|---:|
| Fully discovered hidden FRs | **23/26** | 22/26 |
| Partial hidden FRs | 3/26 | 4/26 |
| Fully missed hidden FRs | 0/26 | 0/26 |

GLM's partial requirements were FR-039 through FR-041. Sol's were FR-038 through FR-041.

Both models made the same central semantic mistake: they preserved pending dialog state on terminal transitions when protocol v2 required clearing it. Sol's version was broader because it also added settlement observation and omitted `terminate-child` on early child exit. On hidden protocol discovery and exact terminal semantics, GLM was therefore marginally stronger.

Neither alignment agent detected the contradiction. Both plans were internally coherent, and their alignment passes validated that coherence instead of re-deriving terminal behavior from the frozen authority. GLM nevertheless scored one point higher in plan alignment.

## Where Sol earned the lead

### 1. Decomposition discipline

The frozen implementation surface contained exactly two files. Sol represented it as one coherent Wave 1 task with source and tests owned together.

GLM produced nine tasks:

- three sequential implementation/test tasks;
- six final-wave ADR-writing tasks;
- four waves in total.

The three core tasks remained within the two-file surface, but the six ADR tasks created files outside it. They added dependencies and ceremony without reducing implementation risk. This explains the largest score difference: Sol earned 18/20 for decomposition while GLM earned 12/20.

### 2. Decision economy and honest sizing

Both architectures separated byte framing, fatal UTF-8/JSON parsing, raw Pi envelopes, parsed ADTs, immutable correlation state, and shell effects. Both were technically credible functional-core designs.

Sol treated reversible local choices as implementation details. GLM promoted six such choices into prospective ADRs. Consequently:

- Sol received 4/4 for decision quality; GLM received 2/4;
- Sol received 4/4 for honest sizing; GLM received 3/4.

This is better understood as a planning-style difference than a protocol-comprehension difference. GLM behaved like a thorough architecture process operating on a larger feature; Sol better calibrated its process to a narrow two-file task.

### 3. Specification compactness

Sol was one point stronger in specification through clearer testability and exact scope. GLM's specification was still strong and discovered one more hidden requirement, but its incorrect terminal postcondition reduced both requirement and testability credit.

### 4. Artifact shaping and recovery

Sol's final plan and graph were more compact and internally aligned with the requested delivery shape. GLM recovered successfully from Loom harness defects, but the recovery loop and oversized task graph reduced process and consistency scores. Harness defects themselves were attributed to Loom rather than model quality.

## Where GLM was equal or stronger

### Protocol discovery

GLM fully discovered 23 requirements versus Sol's 22 and missed none. Its terminal mistake affected three hidden requirements rather than four.

### Verification design

GLM received 4/4 for architecture verification versus Sol's 3/4. Its plan included concrete method/error/framing tables, chunking properties, determinism checks, immutability checks, and mock-free pure-core testing.

### Correlation model

GLM's correlation branch table was implementation-usable. It precisely preserved:

- exact request identifiers;
- request/answer method matching;
- mismatch errors with unchanged state;
- cancellation;
- duplicate suppression;
- response ordering;
- settled no-ops.

The representative rule—method mismatch produces `response-mismatch`, no response, and unchanged state—captured error, effect, and state semantics in one testable branch.

### Independent scrutiny

Both alignment passes failed the decisive authority check, but GLM still scored 5/12 against Sol's 4/12. Sol's alignment report checked both frozen authorities yet declared all four contradictory terminal outcomes covered.

### Mechanical reliability

GLM reached the exact execution boundary with nine pending tasks, no executing work, no forbidden child, exact five-child model attestation, no Cortex contamination, and no frozen-file mutation. The locally hosted runtime remained healthy with zero restarts.

## Interview behavior

Both models scored 6/12, but for different reasons.

GLM asked 21 questions. Several were load-bearing—especially method mismatch, duplicate effects, and settlement behavior—but many asked the operator to restate visible scope, test expectations, and pass criteria. It had better question value than Sol but poor question economy.

Sol asked fewer specification questions but still re-asked authority-fixed UTF-8, terminal, pending, correlation, and audit behavior. It integrated every answer coherently, including the wrong terminal ruling.

The practical GLM weakness is therefore not inability to identify relevant uncertainty. It is insufficient discrimination between facts that require operator input and facts already fixed by authoritative artifacts.

## Interpretation for a locally hosted model

The local GLM result is highly competitive:

- zero hidden requirements fully missed;
- one more requirement fully discovered than Sol;
- a narrower semantic defect;
- stronger verification planning;
- better alignment score;
- complete stop-boundary and routing compliance.

The measured gap mostly reflects concision, scope discipline, and task-graph calibration. It does not demonstrate a comparable gap in core protocol reasoning. A locally served model also provides dimensions this benchmark does not score: data locality, predictable availability, deployment control, and marginal inference economics.

The most defensible conclusion is:

> Sol was better at producing a compact, benchmark-shaped implementation plan. GLM was at least as competitive at discovering and modeling the protocol itself.

## Likely high-leverage GLM guidance

The following orchestration constraints would target the observed weaknesses without giving away hidden protocol answers:

1. Default to one implementation task when source and tests form one atomic two-file change.
2. Do not create ADR tasks for local, reversible decisions unless the brief explicitly requests architecture records.
3. Treat frozen authority as answerable evidence, not an interview topic.
4. Require alignment to reconstruct every terminal transition as an explicit state/effect table before declaring no gaps.
5. Set a task-count and wave-count justification threshold for small-scope changes.

Those controls would likely close much of the measured nine-point gap. That is a hypothesis requiring fresh, isolated repetitions; it should not be retroactively applied to these scores.

## Bottom line

The raw totals are Sol 78 and GLM 69, but the detailed evidence is more favorable to GLM than that headline suggests. Sol's advantage was predominantly planning economy. GLM's actual protocol discovery was slightly better, and both models shared the same central authority mistake. For a locally hosted model, GLM's run is not merely acceptable—it is close enough that workflow calibration may matter more than model scale for this task.
