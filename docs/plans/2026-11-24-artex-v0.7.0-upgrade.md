# ARTEX v0.6.0 → v0.7.0 upgrade (2026-11-24)

## Why

v0.7.0 (released 2026-11-21, tag object `28aab5a8` → commit `22ae88af`) fixes five
advisories, every one of which affects the v0.6.0 we run:

| Advisory | Severity | Issue |
|---|---|---|
| GHSA-m4h4-qcv8-x4c8 | High | Workspace file API exposes the capture-proxy MITM CA private key |
| GHSA-7w8h-wjpx-rxc7 | High | Authenticated SSRF in `POST /api/llm/models` (caller-controlled base_url/proxy) |
| GHSA-9v26-q86m-gcj3 | High | Proxy-routed requests bypass target-gate IP pinning |
| GHSA-wmcc-wqq5-h7m8 | High | Legacy MCP SSE transport POSTs JSON-RPC + Authorization to a server-chosen URL |
| GHSA-fjhc-prxm-c237 | Medium | `OR` in the asset DSL escapes the per-task scope clause |

All need an authenticated session, so the risk at household trust is moderate; it is the
tool that points scanners at targets, and two of them are about staying in scope.
`main` is 189 commits past v0.7.0: not adopted, the pin stays on an audited release tag.

## The audit (planted-code / backdoor), v0.6.0..v0.7.0

Diff: 525 commits (188 merges), 691 files, +87,286 / −9,471. Audit checkouts kept
locally, outside every repo: `~/dev/artex/src-v0.7.0` (clean, at the tag),
`~/dev/artex/norma` (dependency), `~/dev/artex/release-artifacts-v0.7.0`.

- `gh attestation verify … --repo BaaRai/ARTEX`: exit 0. The signed provenance names

  `.github/workflows/release.yml@refs/tags/v0.7.0`, run 44886079686.

- Released `README.md`, `config.example.json`, `start.sh` and the whole `skills/` tree are
  byte-identical to the checkout at the tag.
- The tag is unsigned (as v0.6.0 was); the commit is GitHub's merge of PR #439. v0.6.0 is
  an ancestor of v0.7.0 and no commit in the range landed on main outside a merged PR
  (first-parent non-merge commits: none).

### Dependencies — verified

- **Go**: a fresh `go.sum` derived only from the Go checksum database (empty go.sum,

  search backend (`api.keenable.ai`, only when that backend is selected), outgoing
  tool-result trimming past 70% of the window, redacted-thinking replay. Nothing else.
  The git tag tree is byte-identical to the sumdb-verified module zip.
- **npm (web)**: every `resolved` is `registry.npmjs.org`; no same-name+version entry
  changed integrity; no install scripts; the only new package names are wasm-runtime
  packages bundled (`inBundle`) inside `@tailwindcss/oxide-wasm32-wasi`, not installed on
  amd64. Mostly removals (graphin, fullcalendar, date-fns, zod, …) and bumps (next 16.4.6).
- **npm (skills/api-recon)**: same packages and integrities; registry moved from
  `registry.npmmirror.com` to `registry.npmjs.org`.

### Image inputs — verified

- Base images unchanged (`node:22-bookworm-slim`, `golang:1.26-bookworm`,

  files (projectdiscovery ×4, ffuf, dalfox `.sha256`, nodejs.org `SHASUMS256.txt`): all match.
- New: `npm ci --ignore-scripts`, `NEXT_TELEMETRY_DISABLED=1`, setuid/setgid bits stripped
  image-wide, `/root` 0711, `/app/keys` 0700.

### Source sweep — clean

- **Outbound hosts** added outside tests/docs: `api.github.com` (update check, only with
  `ARTEX_UPDATE_CHECK=1`; GET of `releases/latest`, generic UA, no identifiers),
  `api.keenable.ai` and `api.tavily.com` (search backends, only when selected), plus
  `example.*`/RFC 5737 test hosts. IPv4 literals added are blocklist ranges (metadata
  169.254.169.254 / 100.100.100.200, CGNAT, benchmark, reserved). Web UI: no new absolute
  `fetch`, WebSocket, `sendBeacon` or script tags.
- **Process execution**: v0.6.0 had one site (`server/customtool.go`). New:
  `server/envseal_linux.go` re-execs the server's own binary (`os.Executable`) with the
  secret env vars moved to an inherited pipe (keeps them out of `/proc/<pid>/environ`);
  `server/execpriv_unix.go` is the privilege-drop shim (agent processes, meaning Bash,
  shell, custom tools and MCP stdio, run as uid/gid 10001 instead of root). Both read in
  full: defensive, no hidden targets.
- **Auth**: `requireAuth` still wraps the whole API mux; the exempt set is `/api/auth/*`,
  `/api/health` and the new `/api/ready` (a PG readiness bool). `/api/auth/*` routes are
  unchanged (status, init, login, change-password). New listeners (SOCKS5 TCP/UDP,
  transparent TCP) only start behind their own `ARTEX_*_ENABLED` flags (all unset here).
- No new `init()`, `go:linkname`, cgo or plugin loading; two `unsafe` imports in
  `traffic/`: `stream.go` reaches go-mitmproxy v1.9.2's private `mu` mutex via reflect
  (to read WebSocket/SSE slices without a data race; guarded by `TestLibMutexFound`), and
  `transparent_linux.go` passes a buffer to `getsockopt(SO_ORIGINAL_DST)`. No long
  encoded blobs. The binary-flagged `web/src/components/exploration-graph.tsx` is a NUL
  used as a map-key separator, present identically in v0.6.0. The tamper-hook
  interpreter (`traffic/hookvm`) is opt-in behind `ARTEX_TAMPER_HOOKS_ENABLED`.
- Skills: `bbot-recon` and `rea` only switch to run-dir-relative paths (pairs with the new
  file-tool confinement).

### Scope and limits

This is the same bond as the 2026-11-15 audit: release integrity, dependency integrity,
image inputs, egress hosts, exec sites, auth surface and obfuscation. It is a targeted
sweep plus full reads of the security-relevant new code (exec, envseal, auth, update
check, Norma), not a line-by-line read of all 87k added lines (agent logic, traffic, DB,
UI). CI workflow changes (`ci.yml`, `release.yml`, `bot.sh`) were not reviewed: our image
is built from source by our own workflow, not from their artifacts.

**Verdict: no planted code found; v0.7.0 @ 22ae88af is the new audited identity.**

## The change (branch `artex/v0.7.0`)

- `scripts/artex/build-artex-image.sh` (renamed from `…-v0-6-0.sh`): the audited
  tag+sha are the only hand-written identity; `LOCAL_IMAGE` derives from the sha; the
  verified identity goes to `$GITHUB_ENV` for the publish steps.
- `.github/workflows/build-artex-image.yml`: no hardcoded tag, sha or image name.
- `k8s/argocd-homelab/artex/secrets.enc.yaml`: new `secret-key` (32 random bytes, base64).
- `deployment.yaml`: `ARTEX_SECRET_KEY` from `artex-secrets/secret-key`. Without it,
  0.7.0 mints `/app/keys/secret.key` on the artex-data PVC. The rollback path deletes that
  PVC, and once rows are encrypted a lost key = ARTEX refuses to start.
- `tests/artex-repair-regression.test.mjs`: the new path, plus two invariants (identity
  only in the script; secret key wired from sops). Both were observed RED under mutation.

## Runbook (needs the user's go-ahead: GHCR publish + a live rollout)

1. Push the branch; dispatch the build on it:
   `gh workflow run build-artex-image.yml --ref artex/v0.7.0`. Expect
   `ghcr.io/peterstorm/artex:sha-22ae88af`; record the run id and the digest from the
   run summary.
2. Pin the digest in `deployment.yaml` (and its comment: v0.7.0, run id), commit.
3. **Back up Postgres before ArgoCD sees the new manifest.** The 12 numbered migrations
   and the secrets backfill are one-way:
   `sudo k3s kubectl -n artex exec deploy/artex -c postgres -- pg_dump -U artex -Fc artex > ~/backups/artex/artex-pre-v0.7.0-$(date +%F).dump`
   and confirm `pg_restore -l` lists it.
4. Merge to main and push; ArgoCD syncs (Recreate: brief outage).
5. Verify:
   - pod 2/2 Running;
   - logs show the migrations applied, `[secrets] at-rest encryption ready; backfill
     encrypted N`, `[exec] agent processes run as uid 10001 gid 10001`, no `[env] … not
     sealed`;
   - `curl -s https://artex.peterstorm.io/api/ready` → ready;
   - log in through the ingress and save any setting. That is a cookie POST, so it
     proves the new same-origin check passes behind cilium.
6. Post-upgrade chores: skills turned off before 0.7.0 come back once (re-disable them);
   the untrusted-output boundary is now on by default (left on).

## Rollback

Re-pin the v0.6.0 digest `sha256:519e58f2…` **and** restore the step-3 dump
(`pg_restore --clean`). The DB alone is not backward-compatible: 0.6.0 would read the
`enc:v1:` ciphertexts as literal credentials.
