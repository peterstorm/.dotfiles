# ARTEX on k3s — plan (2026-11-15)

## Goal

Run the audited ARTEX v0.6.0 (BaaRai, AGPL-3.0) as a regular cluster app: argocd-homelab
directory → the `root` ApplicationSet picks it up automatically. Exposed the standard way:
cilium ingress (LAN) **and** a cloudflared tunnel hostname — same twin-route as sonarr, radarr,
grafana, transmission. The LLM is the existing desktop vLLM; no GPU here.

## Provenance (why this image is trustworthy — the CERT-In lesson, institutionalized)

- Source = the audited checkout `~/dev/artex/src` @ tag `v0.6.0` (`a13c68cb`): SHA256SUMS-OK
  release zip, released files byte-identical to the checkout, advisory GHSA-q4j5-2wwq-gmq5
  patched in 0.5.1 (we're past it), every egress host accounted for, ONE exec site, official
  bases, checksum-verified scanner binaries, no Docker Hub involvement.
- The build script refuses to build from anything but the audited tag (see Build below):
  "image ≠ audited source" becomes unrepresentable.

## Exposure — copied, not invented

- Ingress: `ingressClassName: cilium`, `cert-manager.io/cluster-issuer: letsencrypt-prod`,
  host `artex.peterstorm.io`, TLS secret `artex-tls`, backend `service: artex, port: 8787`
  (sonarr/transmission shape, verified live: their VIP 192.168.0.242, 80/443).
- cloudflared/configmap.yaml: one more `- hostname: artex.peterstorm.io` →
  `service: http://artex.artex:8787` (user decision 2026-11-15: tunnel too).
- 8788 (traffic-recording proxy) stays **pod-local**: the harness's own outbound browsing
  uses it via 127.0.0.1; nothing publishes it. (If we ever want it to sit in-path for LAN
  targets, that's a later decision — see Not in scope.)
- The GHSA-takeover window: until first-boot setup completes, an uninitialized 8787 can be
  taken over by whoever reaches it (LAN +, via tunnel, the internet — the "62 consoles"
  story). Mitigation: first-boot ritual immediately at rollout (below). Household-trust
  otherwise; this is the one step that must not slip.

## Layout — one new directory, 8 files

k8s/argocd-homelab/artex/
- deployment.yaml — ONE pod, TWO containers (transmission sidecar spirit, zero
  cross-namespace DNS):
  - `postgres`: image `postgres:16-alpine` (the audited pin), env
    POSTGRES_USER/POSTGRES_DB=artex + POSTGRES_PASSWORD from the secret, volume
    `pgdata` → `/var/lib/postgresql/data`.
  - `artex`: image `ghcr.io/peterstorm/artex:sha-a13c68cb`, `imagePullSecrets:
    ghcr-pull-secret` (dotslash convention — copy that secret stanza into this ns; its
    source-of-truth = wherever dotslash-dev/secrets.enc.yaml defines it — verify when
    writing ours), env: `ARTEX_PG_DSN` =
    `postgres://artex:<PASS>@127.0.0.1:5432/artex?sslmode=disable` (same secret; the
    component-fields config.json path is not used — one string, no second representation),
    LLM endpoint/model/key envs (names confirmed from the checkout docs at bring-up — do
    not guess), `ARTEX_JWT_KEY_DIR=/app/keys` (signing keys on the artex-data subPath)
    and `ARTEX_TRUSTED_PROXIES=10.42.0.0/16,192.168.0.0/24` (login rate-limit trusts
    X-Forwarded-For from the pod CIDR and the LAN), TZ=Europe/Copenhagen. Container port
    8787. Strategy Recreate, replicas 1,
    no resource limits (house norm; the box has headroom — see Gotchas).
  - No readiness/liveness probes: no house precedent, and the PVC+Recreate+single-node
    reality makes them ceremony. (distill: working idiom wins over taste.)
- service.yaml — ClusterIP, port 8787 → targetPort 8787. Single port, so NO port name
  (multi-port = the lesson: unnamed ports are invalid — argocd retried 3× on that mistake).
- ingress.yaml — as in Exposure.
- pvc.yaml — two PVCs, both ReadWriteOnce `local-path`: `artex-pgdata` 5Gi (postgres
  data dir) and `artex-data` 2Gi (mounted at /app/data, and at /app/keys via subPath —
  the JWT signing keys live there; lifecycle note in the deployment comment).
- secret-generator.yaml + secrets.enc.yaml — ksops/sops, keys: `pg-password`,
  `artex-pg-dsn`, `llm-api-key` (+ LLM model/base handled as plain env: they're not
  secret).
- ghcr-pull-secret.enc.yaml — verbatim copy of dotslash-dev's encrypted GHCR pull
  credential (sops blobs are key-encrypted, not namespace-locked); required by the
  deployment's `imagePullSecrets: ghcr-pull-secret`.
- kustomization.yaml — resources: deployment.yaml, service.yaml, ingress.yaml, pvc.yaml;
  generators: secret-generator.yaml. (No configmap needed: skills/ ships inside the image
  at /app/skills, the default skill_dir — verified in the audited Dockerfile.)

Namespace `artex` (created by the ApplicationSet template, CreateNamespace=true).

## Build — provenance-asserting, their sha-tag convention

scripts/artex/build-artex-image-v0-6-0.sh (their scripts/<area>/ convention):
1. `SRC=~/dev/artex/src`
2. assert: `git -C $SRC describe --tags --exact-match` == `v0.6.0` AND
   `git -C $SRC rev-parse HEAD` == `a13c68cb7078d43b66fb398db3d610e513b6d77a` — refuse
   otherwise. This is the audit bond: what we read is what we build.
3. `docker build -t ghcr.io/peterstorm/artex:sha-a13c68cb $SRC` (the audited Dockerfile:
   web→build→tools→runtime; the checksum-verified scanners come along — the pentest
   toolkit travels inside the image, exactly as audited).
4. `docker push` + record `docker inspect --format '{{.Id}}'` in the runbook output.
Note: the tools stage pulls release-checksums over the network at build time; if we ever
rebuild, diffs are expected only in those layers — the app layer stays commit-identical.

## LLM wiring

- Endpoint: `http://192.168.0.80:8000/v1` — desktop vLLM, already reachable from the
  cluster, AND (their own configmap comment) reachable through the WARP private-network
  route when off-LAN. Values as plain env in the deployment.
- Model: whatever the endpoint currently serves (`/v1/models` at bring-up — right now the
  engine runs `ds41-1017-native`; if the GLM cyber profile returns, that's the better
  pentest brain — one env, their call at bring-up).
- Key: from the same source pi's models.json resolves (the api-key file), into the sops
  secret. Confirm the EXACT env names from the checkout's docs (config precedence) when
  writing the deployment — the harness also supports in-app settings; we pin envs so the
  deployment stays the source of truth.
- Headroom: 8 inference slots shared with pi/coding sessions — ARTEX bursts long chains;
  if it ever collides, that's the knob to look at, not a deployment change.

## Bring-up order

1. Build + push the image (script above). Do this FIRST — the deployment pins the sha.
2. `artex/` dir lands in the repo → ApplicationSet auto-creates the Application (namespace
   `artex`, automated+prune+selfHeal, ServerSideApply). Watch: `k3s kubectl -n argocd get
   application artex -o jsonpath='{.status.sync.status} / {.status.health.status}'`.
3. First-boot ritual, immediately: `/setup` via `artex.peterstorm.io` (from LAN or
   tunnel), create the admin — closes the takeover window. Their repo's
   `reset-password.sh` shows the DB-side precedent if the UI path misbehaves.
4. Point the harness's LLM at the desktop endpoint (envs are already in; this is the
   in-app profile/verification step) and run one trivial assessment against a lab target
   (e.g. itself, or an echo target) to prove the scanner toolchain inside the image.
5. Add the cloudflared hostname line + zone record (their terraform-homelab/cloudflare
   owns peterstorm.io — the mechanism that already carries 10+ of these names).

## Gotchas (all discovered, none news)

- Their node disk: 461G, 80% used, ~91G free — the 5Gi PVC is modest; the build costs
  ~2-3GB of docker layer cache before it. Mind it when their 80% creeps.
- ArgoCD will retry-fail visibly on any manifest mistake (the 3×-retry port-name bug) —
  read the Application's operationState message, it says exactly which key is wrong.
- Recreate + 2-container pod: every image bump = brief PG+app outage. Normal here (the
  40-restart transmission precedent); assessments should not be trusted to survive it —
  they're job-shaped anyway.
- sops blobs are key-encrypted, not namespace-locked: the ghcr-pull-secret stanza can be
  copied verbatim into artex/secrets.enc.yaml.

## Rollback

Delete the directory → prune removes the Application's resources (PVC lives until its
own delete; intended — the DB outlives experiments). The image, the audited checkout and
the build script are the only three things to keep if we ever go again.

## Not in scope (deliberate)

- Desktop deployment (nothing there needs it; the LLM already serves cross-machine).
- Publishing 8788 (traffic recording stays pod-internal; in-path MITM for LAN targets =
  its own future decision).
- Public-ingress hardening beyond the house pattern (Access policies, rate limits) — the
  twins live with the arr suite's posture.
- Second replica / HA: Recreate + 1 is the house norm on a single node.
