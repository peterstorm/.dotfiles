**The rule the source enforces** (`slot_take`, `ds4_main.cpp`): a parked
conversation is taken back only when its whole token sequence is a **strict
prefix** of the new prompt — `t.size() < prompt.size() && std::equal(t.begin(),

the model's previous answer included. A hand-made A → B → A+1 probe that drops
the answer saves all three as separate conversations and takes none back; that
is the probe being wrong, not the slot. Receipt:
`~/.local/state/ds41-maya/slots-latest.txt`.

## Split: tensor vs layer (measured 2026-10-22 12:50-13:15)

GPUs 0 and 1 are lopsided — 395 MiB free against 11.2 GiB — because `--tp 2`
makes them **one group**, and every expert is *sharded*: both cards hold their
half of the same expert, so residency is a group decision and the group's
budget is its **tightest member's** free VRAM
(`ds4_model.cu:4052` "per group: what its tightest member has left"; `:4067`
`budget = min(budget, (free - reserve_mib) * vram_experts)`; `--reserve-mib`
600). GPU 0 is the tight member: it carries the head (weights 4.19 GB against
3.61 GB), one more layer's expert set (15,744 slots against 15,360), the
vision tower (318 MiB) and a 1.5 GiB prompt-path reservation while prefill
runs (`:2248`). GPU 1's leftover is therefore unreachable, not wasted by a
leak: `nvidia-smi --query-compute-apps` shows exactly one process on each card.

The obvious lever is `--tp 1`, a **layer split**: each card becomes its own
group, packs experts to its own ceiling, and every layer has one member — the
exact condition `yoco_layer()` wants, so v1.1.19's prompt skip qualifies. A/B
on identical cold prompts (built once, prefixed with a nonce so neither run can
reuse a parked conversation or a KV prefix), 21.3K prompt for prefill and
62.6K + 128 tokens for decode, `scripts/inference/deepseek/ds41-1017-maya/tp-ab-ds41-1017-maya-exl35.sh`
(`TRY_EXTRA` adds flags to the variant; the layer split parks in its own slot
folder and the script removes it on rollback):

| variant | prefill 21.3K | decode @62.6K | `vram_hit` | slots | free VRAM |
|---|---|---|---|---|---|
| tp 2 (base) | 1,988-2,019 tok/s | 73-107 tok/s | 0.9741 | 10,524 | 394 / 11,157 MiB |
| tp 1 | **335 tok/s** | 107 | 0.9818 | 11,750 | 574 / 579 |
| tp 1 + `--threads on` | **2,011 / 2,009** | 104 / 103, 91 | 0.9895 | 11,392 | 462 / 449 |

Three findings:

- **The layer split does reclaim the 11 GiB** — both cards fill to the reserve,
  `vram_hit` 0.9741 -> 0.9895, +868 to +1,226 expert slots in VRAM. Exactly as
  predicted.
- **It serialises the prompt path.** `par = o.threads || tp > 1`, so at tp 1 the
  prompt runs in 16-token windows unless `--threads on` asks for a thread per
  GPU — the engine says so itself: `ds4: prompts run in windows of 16 tokens
  (--tp 1 with --threads off): long prompts prefill far slower than in ...`.
  Prefill 1,999 -> 335 tok/s. With `--threads on` prefill returns to parity
  (2,011 against 1,988) and the skip is active — and still buys nothing.
- **The decode win is noise.** tp 2 decode spread 73-107 tok/s over eight
  samples of the same prompt; tp 1 + threads read 104, 103, 91 — a ~6% edge
  inside that spread. Two samples per config were needed to see it; the first
  run's "+30%" was one sample.

Verdict: **tp 2 stays** — a prompt is read once per conversation (and slots
make the re-reads cheap), while decode runs for every token after it, so
parity in prefill plus an unprovable 6% in decode does not justify a geometry
change that would also need its own slot folder and would be silently undone by
the next `--finish-setup`. The 11 GiB turns out to be worth ~nothing here
because the CPU lane already sees 0.1-0.2% of expert lookups. Receipts:
`~/.local/state/ds41-maya/tp-ab-latest.txt`, `tp-ab-tp1-noargs.txt`,
`tp-ab-tp1-threadsonsingle.txt`, log `tp-ab-20261022-*.log`. The rollback put
`--tp 2` back, deleted the layer split's slot folder and re-gated the engine
(healthy, `restarts=0`, `unless-stopped`, contract PASS).

## Why this quant

- **The Q8 lesson.** UD-Q8_K_XL's ~305 GB of non-Engram weights against
  191 GB VRAM + ~76 GB engine heap left ~100 GB of cold experts on the NVMe;
  the drive ran flat out at 9.7 GB/s while the GPUs idled at 0-4%: 5.2 tok/s
  sustained in calibration, 1.4-1.8 tok/s and ~12 tok/s prefill on reclaw's
  11K-token agent turns.
- **EXL3 3.5 bpw fits.** 257.6 GB of weights; Maya sizes it at **~280 GB of
  VRAM + RAM** to hold everything (`DS4_EXL3["exl3-3.5"].memory_gb` in
  `maya.py` at the pinned commit). This box has 191 GB VRAM + ~85 GB of free
  RAM ≈ 276 GB, so VRAM keeps 10,908 of 15,744 experts on GPU 0 and 10,524 of
  15,360 on GPU 1 (the boot banner's own counts, 256K context), and the rest
  are read **in place from the model files** by the
  CPU lane, and the engine keeps an anonymous heap copy of the most-routed
  ~72 GiB (`RssAnon` 72.2 GiB against `RssFile` 218 MiB, `VmLck 0` — its own
  buffer, not page cache) — **not a pinned RAM tier** (`ram_experts: 0` in
  `/metrics`; `--glm-ram-resident` is off). That is why only ~2% of expert lookups reach
  the CPU lane instead of Q8's ~100 GB of cold experts. If a boot shows a
  larger CPU share, shrink `CONTEXT` (65536 → 32768) to give the expert pool
  more VRAM.
- **Quality.** The quant card: perplexity over the unquantized model +0.8%
  (code) / +0.1% (prose) — closer to the original than the 2.9 bpw
  (+1.8% / +0.4%, 230 GB, the fallback if 3.5 still spills).
- **Engram.** EXL3 repos carry no Engram tables; Maya takes them from
  DeepSeek's 1017 base repo as safetensors (the 1017 release changed them —
  the older V4.1's must not be used). unsloth's MXFP8 GGUF shard of the same
  tables is not read by the EXL3 path, so it was not kept.

## Procedure

All scripts are in `scripts/inference/deepseek/ds41-1017-maya/` and run **on the
desktop** (they probe `docker`, `nvidia-smi`, `mountpoint`). The desktop's own
`~/.dotfiles` checkout lags (41f968e on 2026-10-22) and does **not** contain this
directory — `--preflight` fails there; the deployment runs from a copy at
`~/.local/share/ds41-maya/repo`, synced from the repository (`machines/` and
`scripts/inference/`), whose four scripts are byte-identical to the repository
versions. Sync that copy before relying on it; it currently carries `deepseek/`
and `shared/` but **not** `glm53/`, so the "back to v15" step needs that
directory copied too.

```bash
cd ~/.local/share/ds41-maya/repo/scripts/inference/deepseek/ds41-1017-maya

./download-ds41-1017-maya-exl35.sh --status
journalctl -fu ds41-1017-maya-exl35-download

./run-ds41-1017-maya-exl35.sh --preflight

# cutover window (Pi is offline from here until the switch accepts)
../../glm53/switch-glm53-qad2-tp2-v15.sh stop
./run-ds41-1017-maya-exl35.sh --finish-setup
./switch-ds41-1017-maya-exl35.sh start

# back to v15 (stop Maya first: its /metrics is auth-gated, so the vLLM
# switcher's idle gate cannot read it and refuses the cutover)
./switch-ds41-1017-maya-exl35.sh stop
../../glm53/switch-glm53-qad2-tp2-v15.sh start

# what is actually serving
curl -s http://127.0.0.1:8000/health | jq '{model, max_context, images, defaults}'
set -a; . ~/.config/ds41-maya/server.env; set +a
curl -s -H "Authorization: Bearer $STRATA_API_KEY" http://127.0.0.1:8000/metrics \
  | jq '{engine: (.engine | {expert_slots, cpu_experts, ram_experts, kv, kv_resident}), live}'
```

**Engine upgrade or rollback (same-container binary swap).** The switcher's
rollback is wrong for this: it would restart the new, failed binary. Use the
one-shot script, which stops, pins, rebuilds, launches, proves a real
completion, and rebuilds the old commit again if anything fails:

```bash
# upgrade (defaults: NEW=b3fa99e, OLD=8d9a9b5) or roll back with NEW=<old> OLD=<new>
scripts/inference/deepseek/ds41-1017-maya/cutover-ds41-1017-maya-exl35.sh
tail -f ~/.local/state/ds41-maya/cutover-*.log
cat ~/.local/state/ds41-maya/cutover-latest.txt   # commit, pin, engine sha256, stamp, placement, GPUs
```

It is idempotent in the useful sense: it stops, pins, rebuilds and verifies
whatever `NEW` names, so re-running it on the current commit repairs a
damaged engine. Give it a delay (`… 120`) to let an in-flight generation
finish before the container stops.

By hand the same steps are: `switch-ds41-1017-maya-exl35.sh stop`; set both
copies of `MAYA_COMMIT` (`~/.local/share/ds41-maya/repo/…` and the repository);
`git -C /models/ds41/project-maya checkout <commit>`; rebuild inside the pinned
image (the cmake line in the script); regenerate `build/MAYA-BUILD.json`; then
`run-ds41-1017-maya-exl35.sh --launch` and `docker update --restart=unless-stopped`.
The engine must be **down** for the rebuild: the running container holds the
old binary open.

Run the long steps (`--finish-setup`, `start`, benchmarks) as transient system
units (`sudo systemd-run --uid … --gid …`): the user has no linger, so
anything started from an ssh session dies when it closes.

## Gotchas

- **The dataset now mounts at boot** (proven 2026-10-22 08:22: both ZFS
  datasets mounted at 08:22:23/08:22:25, before dockerd started at 08:22:58, and
  the container came up at 08:23:31). Generation 74 carries the `fileSystems`
  entries (`/etc/fstab` lists both; `models-ds41*.mount` are active). Booting an
  **older generation** still leaves `/models/ds41` empty — the 2026-10-21 boot
  on generation 73 made the Q8 container (restart=unless-stopped) crash-loop
  with `maya.sh: No such file or directory` (exit 127) — and the mount is then
  by hand: `sudo mount -t zfs rpool/models/ds41 /models/ds41 && sudo mount -t
  zfs rpool/models/ds41/engram /models/ds41/engram`.
- **The desktop runs generation 74, built from the Aug 14 lock.** The Oct 7
  flake.lock (root nixpkgs `b4fd65b`) fails to build on the desktop:
  `cuda13.3-nccl-2.32.3-1`'s source
  (`github.com/NVIDIA/nccl/archive/refs/tags/v2.32.3-1.tar.gz`) no longer
  matches its pinned hash (specified `sha256-xUllfd…i6g=`, got
  `sha256-GnawQU…SY4=`), which fails every ComfyUI package on it; it would
  also move the kernel 6.18.44 → 6.18.54 and NVIDIA 595.91.07 → 595.104.02.
  Generation 73 had been built from commit `1d6f57a`'s lock (root nixpkgs
  `0e251e2`), so generation 74 (2026-10-21 20:05) is that lock plus only the
  two dataset mounts, verified before the switch (`diff-closures`: same
  kernel and packages; `/etc` and initrd differ only by the two mounts):
  ```
  git show 1d6f57a:flake.lock > /tmp/gen73.flake.lock
  nix build .#nixosConfigurations.desktop.config.system.build.toplevel \
    --reference-lock-file /tmp/gen73.flake.lock --no-write-lock-file --print-out-paths
  sudo nix-env -p /nix/var/nix/profiles/system --set <out>
  sudo <out>/bin/switch-to-configuration switch
  ```
  A plain `system-apply.sh` builds the Oct 7 lock again: it fails until
  nixpkgs fixes the NCCL hash, and then brings the kernel/driver update
  (reboot).
- **The EFI boot pin outlives generations.** The headless boot default is
  pinned with `bootctl set-default` (gaming runbook), which names one
  generation's entry file: after the 2026-10-21 hard reset the desktop booted
  generation 73 (no ds41 mounts) although 74 was current. `system-apply.sh`
  now moves an existing pin to the new generation's headless entry; a manual
  build/switch (as for generation 74) must do the same:
  `sudo bootctl set-default <id of title "NixOS", version "Generation N ...">`.
- **Never `cp` model files on this pool**: OpenZFS 2.4 block-clones them and
  the copy keeps the source's record size. Use `dd` or download in place.
- **Maya answers any model id.** After the Q8 cutover, reclaw's Pi
  (homelab, 192.168.0.28) kept sending its GLM turns to `:8000` and Maya served
  them (reclaw is now pinned to `deepseek-v4.1-flash:low`). Pi's `desktop-vllm`
  catalog still lists all thirteen profiles on the same endpoint, with windows
  from 262K up to 1M — far larger than Maya's 262,144: selecting any id but
  `deepseek-v4.1-flash` mis-sizes the prompt budget. Only the id for the
  profile that is actually up is safe.
- **A manual stop outlives reboots.** `restart=unless-stopped` means "restart
  unless an operator stopped it", and that stop persists: after the 2026-10-22
  reboot the container did not come back by itself — the switcher recreated it
  at 08:23:31 (`Created == StartedAt`, `RestartCount 0`). `switch-ds41-1017-
  maya-exl35.sh start` is idempotent: if the container is already up it
  re-verifies health/model, rewrites the boot receipt and re-promotes the
  restart policy instead of recreating it.
- **Maya's `/metrics` needs the key** (401 without it), unlike vLLM's. The
  switchers' idle gate (`curl -fsS /metrics`) therefore cannot see Maya's load:
  starting v15 while Maya is busy would stop it mid-request. The procedure
  above stops Maya first, which is the safe order.
- **The engine and `.venv` belong to the toolchain image**; the checkout must
  stay at `MAYA_COMMIT` and clean; `MAYA_UPDATE_CHECK=0` keeps the dashboard
  from `git pull`-ing it.
- **RAM:** at 256K the container holds 76.3 GiB, of it 72.2 GiB anonymous
  heap (`RssAnon` — the engine's own copy of the most-routed experts; 218 MiB
  `RssFile` proves it is not page cache, `VmLck 0` proves nothing is pinned);
  the host then shows 92 of 91.9 GiB used and ~2.9 GiB available. ComfyUI and
  other RAM- or GPU-heavy work must stay stopped.
- **The long-prompt skip is off for this profile** (`--tp 2`): `yoco_layer()`
  returns -1 unless every layer has one member on one device
  (`l.nm != 1 || l.dev != L[0].dev`), so v1.1.19's skip and
  `MAYA_DS4_PROMPT_SKIP` do nothing here; only a layer split qualifies, and
  #343 extends it to 2-GPU layer splits only. Do not expect the release notes'
  1.5x prefill — and the 2026-10-22 A/B shows that even with the skip active a
  layer split is no faster (see **Split: tensor vs layer**).
- **GPU 0 is nearly full** (395 MiB free against GPU 1's 11.2 GiB): it carries
  the vision tower (318 MiB), the output head and one more layer's experts, and
  under `--tp 2` the pair is one group whose expert budget is the *tightest*
  member's, so GPU 1's slack is unreachable by design (see **Split: tensor vs
  layer** — the layer split that would reclaim it measured worse). Nothing else
  may allocate on GPU 0; an extra CUDA client there will fail.
- **`/health.version` is null at this pin** (upstream ships an empty tracked
  `VERSION` at `b3fa99e`). Provenance: container label
  `ai.peterstorm.inference.maya-commit`, `build/MAYA-BUILD.json`, the cutover
  receipt. Filling `VERSION` in dirties the pinned checkout.
- **The engine log rotates per boot** (`/models/ds41/project-maya/maya-ds4.log`
  collects the current boot's `ds4:` placement lines and every `serve:` timing
  line). `/metrics` is the live source: `expert_slots`, `cpu_experts`,
  `ram_experts`, `kv_resident`, `tiers.*` and the last requests' `reused` counts.
- **WiFi:** both ethernet ports are down (NO-CARRIER); the desktop is on
  2.4 GHz WiFi (~19 MB/s).
