## Why this profile

The goal is the highest quality DeepSeek-V4.1-Flash-1017 on 2× RTX PRO 6000
(192 GB VRAM) + 96 GB RAM, with as much as possible on the GPUs and the rest
in RAM and on the SSD.

- **Quant: unsloth UD-Q8_K_XL.** DeepSeek ships 1017 with FP4 routed experts
  and FP8 everything else, so "native" is the ceiling: UD-Q8_K_XL keeps the
  experts in the released MXFP4, dense weights BF16, Engram MXFP8. unsloth's
  measurement: KL 0.0048 / 98.5% same top-1 (wiki), 0.0028 / 98.7% (long17k).
  Non-Engram weights 305.6 GB, Engram 202.8 GB.
- **Engine: Project Maya `maya-ds4`.** The only engine found that combines
  per-expert hot placement in VRAM (not per layer), a two-GPU split, a RAM
  then SSD tier through the page cache, and a reader for unsloth's GGUF.
  Rejected: Xolotl (one GPU, GSQ 2-3 bit only), ik_llama.cpp / llama.cpp
  PR #30817 (per-layer `-ot` split: GPUs carry ~58% of routing), vllm-exl3
  2×PRO-6000 recipes (~250 GB host RAM, Engram pinned in RAM), Karmic Kraken
  `ds41-flash` (TP4 only, no offload), KTransformers (~420 GiB RAM),
  dsv41-flash-offload (one GPU, all experts pinned in RAM).
- **Placement expectation:** ~180 GB of the hottest experts + dense weights on
  the GPUs, ~60 GB in RAM (Maya pins all but ~6 GB of free RAM), ~45 GB of the
  coldest experts read from the NVMe while answering; Engram rows from the
  NVMe. The SSD share is what decides the speed — measure, don't predict.
- **Fallback if too slow:** LibertAIDAI EXL3 3.5 bpw (`--ds4-quant exl3-3.5`,
  ~280 GB of VRAM + RAM, fits without SSD reads). Only one fits on disk with
  the other: delete the Q8 files first.

## Storage

`rpool/models/ds41`: `recordsize=1M`, `compression=off`,
**`primarycache=metadata`**. Maya mmaps the GGUF and the Linux page cache
holds the experts that fit in RAM; with ARC also caching data, the same
bytes would be held twice on a 96 GB machine. Maya (≥ v1.0.33, #89) counts
ARC's reclaimable memory as free when it sizes its RAM tier.

## Procedure

All scripts are in `scripts/inference/deepseek/ds41-1017-maya/`.

```bash
# progress
./download-ds41-1017-maya-q8.sh --status
journalctl -fu ds41-1017-maya-q8-download

# when complete: pins + files
./run-ds41-1017-maya-q8.sh --preflight

# cutover window (Pi is offline from here until the switch accepts)
../../glm53/switch-glm53-qad2-tp2-v15.sh stop
./run-ds41-1017-maya-q8.sh --finish-setup     # re-verifies 508 GB, drafter, vision, pack, calibration
./switch-ds41-1017-maya-q8.sh start           # launch -> accept -> receipt -> promote

# back to v15
./switch-ds41-1017-maya-q8.sh stop
../../glm53/switch-glm53-qad2-tp2-v15.sh start
```

`switch-ds41-1017-maya-q8.sh start` with v15 still running runs the vLLM idle
gate first and restarts v15 on any launch or acceptance failure. v15's own
switcher reads vLLM's `/metrics`, which Maya does not serve in that format,
so going back is always `stop` first, then v15's `start`.

## Gotchas

- **The engine and `.venv` belong to the toolchain image.** `.venv/bin/python`
  links to the image's `/opt/venv` Python. Running `./maya.sh` on the NixOS
  host, or in another image, breaks it. The checkout must stay at
  `MAYA_COMMIT` and clean (the run script refuses otherwise).
- **Maya's self-update is off** (`MAYA_UPDATE_CHECK=0`): its dashboard can
  `git pull` and recompile in place, which would move the pinned commit. Bump
  `MAYA_COMMIT` deliberately, then `--finish-setup` again.
- **RAM:** while Maya runs it pins all but ~6 GB of free RAM. ComfyUI and
  other GPU or RAM-heavy work must stay stopped.
- **WiFi:** both ethernet ports are down; the desktop is on 2.4 GHz WiFi
  (channel 3). Any re-download is ~8 h until a cable or 5/6 GHz link is used.
- `rpool/models/native-l2` (512G quota, empty) was the DS4 r31/r18 KV tier and
  has no user left; it is still declared in `disks.nix`.
